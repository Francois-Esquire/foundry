---
title: Safety and Limits
description: What dry execution substitutes and what your code can still do.
---

Marbles executes local TypeScript with the authority of its host process. It is
not a security sandbox or permission-management system. Environment variables,
tokens, filesystem access, and network access remain available according to that
process's environment and permissions.

## Dry execution

`--dry-run` changes only what Marbles owns. Agent turns are echoed instead of sent,
and `generate().text` is the echoed prompt. Git commands issued through
`workspaces` are printed and not run. Sandbox commands are printed and return
exit 0 with empty output, so a failure branch never runs under `--dry-run`.
Nothing is written under the state root or the artifact store: runs,
schedule history, monitor observations, sessions, grants, and feed entries
live in memory and end with the process, and a run parked on a question is
cancelled at quit.

Step bodies still execute ordinary code and can produce side effects. A raw
`fetch`, a file write, or a child process in a body happens for real. File
monitors still scan, HTTP monitors still use the network, and Git status can
still read the working tree. Worktree helpers still allocate a temporary
directory even though their Git commands are echoed. Clients and tools you
construct independently do not inherit these substitutions. Read the bodies
before running `roll` on a module you did not write.

:::note
Under `--dry-run`, `launchd install` and `launchd uninstall` print what they
would do (the plist and the `launchctl` commands) instead of changing
LaunchAgent files. Use `--dry-run`
to inspect managed execution, not to contain arbitrary code.
:::

## Agents and authority

A working directory sets context, not a security boundary, and a sandbox
mounts the step's workspace read/write. A prompt asking an agent not to edit
is a agent instruction, not an enforceable permission. Authentication and
available tools belong to the installed Claude Code or Codex CLI. Review their
configuration before granting an automation access to your work.

LaunchAgent jobs run as the installing user. Marbles exits between launchd ticks;
it is not a resident daemon. Schedule locks skip overlapping ticks for the same
workspace and key. They do not coordinate every action or custom side effect
across your machine.

## Continuity has boundaries

State is saved to disk. Run history, schedule outcomes, monitor observations,
agent sessions, and declared artifacts survive separate invocations. A run
parked on a question or a pause survives a quit, a crash, or a kill, and is
adopted by the next dashboard that can answer it. A run that was mid-body when
its process stopped is not resumed; its finished steps keep their results, and
`status` marks it orphaned. Cancellation stops what Marbles opened and cannot
undo side effects already made. Model judgments and conversation history do
not guarantee correctness.

Explorations in the use-case section are application blueprints, not a hosted
service, desktop application, or general-purpose personal assistant.
