`@foundry/eslint-plugin` checks prompts without running the code. The
linter parses the file and walks it; the plugin's rules pick out the
prompts, hand their text to `@foundry/prompts`, and report each finding
where it was written. The same file loads in ESLint and in Oxlint, and the
editor extension for either one shows the findings inline.

## What is checked

The rules read tagged templates and calls on a member named after a stock
dialect, on any object: `prompts.claude`, `mine.codex("…")`, `x.pi`. A call
counts when its only argument is a string literal or a template literal
with no substitutions. A `${}` inside a tagged template is a hole, and
nothing is ever reported across one: a reference built at runtime is
dynamic, not unknown.

| Rule | Reports |
| --- | --- |
| `no-unresolved-reference` | A skill or agent that nothing listed has, and a command or variable the harness does not know. |
| `no-foreign-notation` | A skill or agent you have, written the way another harness reads it: `$review` in a Claude Code prompt, where it should be `/review`. |
| `no-template-only` | `$ARGUMENTS`, `${CLAUDE_SKILL_DIR}`, `` !`cmd` `` and the like in a message, where the harness sends them as literal text. |
| `no-consumed-by-harness` | A message the harness acts on itself, such as `/clear` or `!git status`, so the model never receives it. |

Each diagnostic code is its own rule, so each has its own severity. The two
codes about interpolated values, `misread-reference` and
`unsupported-reference`, need the value and are left to the tag at runtime.

The first two rules need to know what exists. Until you list skills or
agents, no skill or agent is questioned and no sigil is called foreign.
Commands and harness variables are checked against each dialect's
built-ins regardless, so `prompts.codex` opening with `/nope` is reported
with no configuration at all.

## Setup

The plugin is internal to Foundry for now, like `@foundry/prompts`. Point
it at your skills and agents; the settings are shared by every rule.

```js
// eslint.config.js
import tsParser from "@typescript-eslint/parser";
import foundryPrompts from "@foundry/eslint-plugin";

export default [
  {
    files: ["**/*.ts"],
    languageOptions: { parser: tsParser },
    ...foundryPrompts.configs.recommended,
    settings: {
      foundryPrompts: {
        skills: [".claude/skills", "plugin:lint"],
        agents: [".claude/agents"],
      },
    },
  },
];
```

```jsonc
// .oxlintrc.json
{
  "jsPlugins": ["@foundry/eslint-plugin"],
  "rules": {
    "foundry-prompts/no-unresolved-reference": "error",
    "foundry-prompts/no-foreign-notation": "error",
    "foundry-prompts/no-template-only": "warn",
    "foundry-prompts/no-consumed-by-harness": "warn"
  },
  "settings": {
    "foundryPrompts": { "skills": [".claude/skills"], "agents": [".claude/agents"] }
  }
}
```

| Setting | Meaning |
| --- | --- |
| `skills`, `agents` | Names, or directories to list. An entry with a slash or a leading dot is a directory. A skills directory contributes its subdirectory names, as in `.claude/skills/<name>/SKILL.md`; an agents directory contributes its `.md` file names. Paths are relative to the linter's working directory. |
| `dialects` | Extra member names and the stock dialect each reads as: `{ "house": "claude" }` checks `mine.house` from `assemble`. |
| `surface` | `message` by default. Set `template` for code that writes skill and command files, where `$ARGUMENTS` and inline shell belong. |

Nothing is discovered beyond what is listed. A directory is read with one
`readdir` and the listing is kept for two seconds, so a new skill shows up
in the editor without a read per prompt.

`configs.recommended` is an ESLint flat config object with every rule on,
errors as errors and warnings as warnings. Oxlint's JS plugins are alpha;
the plugin's tests run `oxlint` over the sample files to prove it loads.

## In the editor

The ESLint and Oxc extensions for VS Code read the same config and
underline each finding, with the message in the Problems panel. Nothing in
[the Foundry Prompts extension](/prompts/editor) runs for this: it colours
references, and the linter checks them.

## Limits

- **References by value.** `${ref.skill("x")}` and a `defineSkill` value are
  holes to a static rule. The tag checks them at runtime; a type-aware check
  is a later step.
- **Skill and agent files.** `SKILL.md` and `.claude/agents/*.md` are not
  linted yet. ESLint could read them through `@eslint/markdown`; Oxlint
  cannot.
- **Biome.** Biome's plugins are GritQL patterns, which cannot call
  `@foundry/prompts`. A Biome rule would have to re-encode each notation
  as a regex, so there is none; that changes if Biome ships JS plugins.
